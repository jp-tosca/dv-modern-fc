## Summary

Legacy JSF gives superusers a "Move Dataset" page on the administrative dashboard for relocating a dataset from one collection to another: pick the dataset, pick the destination collection, submit, and confirm. The new frontend has no equivalent — no move route or component exists, and because the SPA has no dashboard at all, there is no entry point either. A superuser must return to the legacy JSF UI to move a dataset.

## Legacy JSF behavior

`dashboard-movedataset.xhtml` renders two panels — "Dataset to move" with a `sourceDatasetMenu` type-ahead (by persistent ID) and "New dataverse collection host" with a `destinationDataverseMenu` type-ahead — plus "Save Changes" and "Cancel". Submitting validates the pair and raises a confirmation dialog before the move is executed.

### Steps to observe

1. Log into the legacy JSF app (http://localhost:8080) as a superuser (`dataverseAdmin`).
2. Open the dashboard (`/dashboard.xhtml`) and click "Move Dataset" in the Data card, or go straight to `/dashboard-movedataset.xhtml?dataverseId=1`.
3. Observe the "Dataset to move" field ("Enter Dataset Persistent ID, doi:...") and the "New dataverse collection host" field ("Enter Dataverse Identifier...").
4. Select a dataset and a destination collection, click "Save Changes", and observe the confirmation dialog before the move is applied.

## New frontend behavior

There is no move functionality of any kind in the SPA. A case-insensitive search across `src/` for `moveDataverse`, `moveCollection` and `moveDataset` returns no matches, `Route.enum.ts` contains no move route, and there is no dashboard route to reach one from. Navigating to a plausible move URL falls through to the SPA's 404 page.

### Steps to reproduce

1. Open the modern frontend (http://localhost:8000/modern).
2. Note there is no dashboard entry in the header for a superuser (see jp-tosca/dv-modern-fc#5).
3. Navigate directly to http://localhost:8000/modern/dashboard/move-dataset.
4. Observe the redirect to `/modern/404` — the route is not registered, so no move-dataset UI exists to permission-gate in the first place.

## Expected behavior

A superuser should be able to move a dataset to a different collection from the new frontend: choose the dataset, choose the destination collection, review a confirmation of the planned move, and apply or cancel it — with the same superuser-only gating as legacy.

## Current behavior

Absent. No route, no component, no menu entry, and no "Not Implemented" placeholder — there is nothing to click. The backend already exposes `POST /api/datasets/$id/move/$alias`, so only the UI is missing.

## Acceptance criteria

- [ ] A superuser can reach a move-dataset view in the new frontend
- [ ] The view lets the user find and select the dataset to move (by persistent ID or search)
- [ ] The view lets the user find and select the destination collection
- [ ] Submitting shows a confirmation summarising the planned move, which can be confirmed or dismissed without moving
- [ ] Confirming moves the dataset and reports success or a validation failure (for example a duplicate persistent identifier or a guestbook/template conflict)
- [ ] The view is not reachable by non-superusers
- [ ] Covered by an automated test for a successful move and for a rejected move
