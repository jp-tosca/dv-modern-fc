## Summary

Legacy JSF gives superusers a "Manage Harvesting Server" page that turns this installation's OAI-PMH server on or off and defines the OAI sets (search-query-defined collections of local datasets) that remote harvesters can pull. The new frontend has no harvesting-server administration at all — no route, no component, no strings.

## Legacy JSF behavior

`harvestsets.xhtml` shows an "OAI Server" enable/disable control ("Disabled" on a fresh install) and, once the server is enabled, an "Add Set" button plus a list of sets. Each set is created through a short wizard (define the search query, then name and describe the set) and can afterwards be edited, exported on demand ("Run Set Export Now"), or deleted, with a cancellable dialog.

### Steps to observe

1. Log into the legacy JSF app (http://localhost:8080) as a superuser (`dataverseAdmin`).
2. Open the dashboard and click "Manage Server" on the Harvesting Server card, or go to `/harvestsets.xhtml`.
3. Observe the "Manage Harvesting Server" page with the "OAI Server" control showing "Disabled".
4. Enable the OAI server to reveal "Add Set" and the set-management actions.

## New frontend behavior

There is no harvesting-server UI in the SPA. A case-insensitive search for `harvest` across `src/` and `public/locales/` returns only the homepage *harvested datasets* metric, and `Route.enum.ts` has no harvesting route. There is also no dashboard from which to reach one.

### Steps to reproduce

1. Open the modern frontend (http://localhost:8000/modern).
2. Note there is no dashboard entry for a superuser (see jp-tosca/dv-modern-fc#5).
3. Navigate directly to http://localhost:8000/modern/dashboard/harvesting-clients (or any harvesting path).
4. Observe the redirect to `/modern/404` — no harvesting route of any kind is registered.

## Expected behavior

A superuser should be able to administer the harvesting server from the new frontend: toggle the OAI-PMH server on or off, list existing OAI sets, create a set from a search query with a name and description, edit it, trigger its export on demand, and delete it — with the same superuser-only gating as legacy.

## Current behavior

Absent. No route, no component, no i18n strings, no placeholder. The backend already exposes `/api/harvest/server/oaisets`, so only the UI is missing; administrators must use the legacy JSF page or the API.

## Acceptance criteria

- [ ] A superuser can reach a harvesting-server view in the new frontend
- [ ] The OAI-PMH server can be enabled and disabled from it, with the current state shown
- [ ] Existing OAI sets are listed
- [ ] A set can be created from a search query with a name and description, and the flow can be cancelled without creating it
- [ ] A set can be edited, deleted, and exported on demand
- [ ] The view is not reachable by non-superusers
- [ ] Covered by automated tests for toggling the server and for creating and deleting a set
