## Summary

Legacy JSF can let users choose which notifications they receive, separately for email and in-app delivery, from a "Notification settings" panel on the Notifications tab. **This panel is opt-in per installation: it only appears when an admin enables the `:ShowMuteOptions` database setting, which is `false` by default.** The new frontend's Notifications tab lists and dismisses notifications but has no muting controls, so on an installation that has turned muting on, users of the new frontend can't opt out of any notification type, including the emails.

> [!IMPORTANT]
> **You won't see this feature on a default installation.** The legacy panel is hidden unless `:ShowMuteOptions` is set to `true`. See [Enabling the feature](#enabling-the-feature-legacy-jsf) below before trying to reproduce.

## Enabling the feature (legacy JSF)

Notification muting is controlled by three installation-wide **database settings**. They're stored in the `setting` table, have no admin UI, and are managed through the admin settings API (usually only reachable from localhost or with the API unblock key):

| Setting | Default | Effect |
|---|---|---|
| `:ShowMuteOptions` | `false` | When `true`, shows the "Notification settings" panel on the Notifications tab. When unset or `false`, the panel is not rendered at all. |
| `:AlwaysMuted` | empty | Comma-separated notification types (e.g. `ASSIGNROLE,REVOKEROLE`) that are always muted. Users can't turn them on. |
| `:NeverMuted` | empty | Comma-separated notification types that are never muted. Users can't turn them off. |

Types listed in `:AlwaysMuted` or `:NeverMuted` show in the panel as greyed-out (disabled) checkboxes. If a type appears in both, `:AlwaysMuted` wins and a warning is logged. These settings were added in Dataverse 5.11.

```bash
# Enable the panel
curl -X PUT -d true http://localhost:8080/api/admin/settings/:ShowMuteOptions

# Optional: lock some types so they show as disabled checkboxes
curl -X PUT -d 'ASSIGNROLE,REVOKEROLE' http://localhost:8080/api/admin/settings/:AlwaysMuted
curl -X PUT -d 'CREATEACC' http://localhost:8080/api/admin/settings/:NeverMuted

# Check the current value
curl http://localhost:8080/api/admin/settings/:ShowMuteOptions

# Revert to default (panel hidden)
curl -X DELETE http://localhost:8080/api/admin/settings/:ShowMuteOptions
```

Docs: Installation Guide → [`:ShowMuteOptions`](https://guides.dataverse.org/en/latest/installation/config.html#showmuteoptions), [`:AlwaysMuted`](https://guides.dataverse.org/en/latest/installation/config.html#alwaysmuted), [`:NeverMuted`](https://guides.dataverse.org/en/latest/installation/config.html#nevermuted). User Guide → [Notifications](https://guides.dataverse.org/en/latest/user/account.html#notifications).

## Legacy JSF behavior

With `:ShowMuteOptions=true`, `dataverseuser.xhtml` renders a collapsible "Notification settings" panel above the notification list. It has two multi-select checkbox groups and a "Save Changes" button:

- `notification.mutedEmails`: "Select the email notifications you wish to receive:"
- `notification.mutedNotifications`: "Select the in-app notifications you wish to receive:"

Unchecking a type mutes that notification for that delivery channel. Users can also manage the same preferences through the API: `GET /api/notifications/mutedEmails`, `PUT`/`DELETE /api/notifications/mutedEmails/{typeName}`, and the same endpoints for `mutedNotifications`.

### Steps to observe

1. Enable the setting as a superuser: `curl -X PUT -d true http://localhost:8080/api/admin/settings/:ShowMuteOptions` (see [Enabling the feature](#enabling-the-feature-legacy-jsf)).
2. Log into the legacy JSF app (http://localhost:8080) as `dataverseAdmin`.
3. Go to Account → Notifications (`/dataverseuser.xhtml?selectTab=notifications`).
4. Expand "Notification settings".
5. You should see the two checkbox groups for email and in-app notification types. Uncheck one and click "Save Changes" to mute it.

## New frontend behavior

The SPA Notifications tab (`/modern/account?tab=notifications`) shows "Displaying 1 - N of N Notifications", each row with a dismiss (X) control, plus a "Clear All Notifications" action. There is no settings panel and no muting UI, whatever the value of `:ShowMuteOptions`. A case-insensitive search for `mute` across `src/sections/account/notifications-section/` and `public/locales/en/account.json` finds nothing.

### Steps to reproduce

1. Enable `:ShowMuteOptions` on the backend as above.
2. Log into the modern frontend (http://localhost:8000/modern) as `dataverseAdmin`.
3. Open the user menu and choose "Notifications" (or go to `/modern/account?tab=notifications`).
4. You'll see the notification list with dismiss and "Clear All Notifications", and no notification-settings or muting control anywhere on the tab.

## Expected behavior

When the installation has `:ShowMuteOptions=true`, users should be able to choose, per notification type, whether they get it by email and whether it appears in-app, the same way legacy's two checkbox groups work. The choice should be saved to their account. Types locked by `:AlwaysMuted` / `:NeverMuted` should be shown but not editable. When `:ShowMuteOptions` is false (the default), no muting UI should be shown, which matches legacy.

## Current behavior

The SPA has no muting. On an installation with muting enabled, users can only dismiss notifications after they arrive. They can't stop unwanted notification emails without going back to the legacy JSF page or using the API.

## Acceptance criteria

- [ ] The notification settings UI is shown only when `:ShowMuteOptions` is `true` and is hidden by default
- [ ] The Notifications tab offers per-type control over which notifications the user receives by email
- [ ] It offers the same control for in-app notifications, separately from email
- [ ] Types listed in `:AlwaysMuted` / `:NeverMuted` are shown as disabled and can't be changed
- [ ] Choices are saved to the user's account and still show after a reload
- [ ] Muting a type stops the email and/or the in-app entry for that type, depending on which channel was muted
- [ ] Existing list, dismiss and "Clear All Notifications" behavior is unchanged
- [ ] An automated test checks that a muted type is saved and that the UI is hidden when `:ShowMuteOptions` is false
